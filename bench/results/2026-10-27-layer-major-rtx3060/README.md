# Qwen streamed-expert layer-major measurements

Structured run-level results are in [results.json](results.json). They were captured with the repository harness on Windows x64, an Intel Core i5-14600K, NVIDIA GeForce RTX 3060 12 GB (driver 610.74), CUDA 13.3.73, and the Swift Qwen3.8-Flash-Next IQ3_XXS pack. Runs used `--prefill auto`, 1,000 expert-cache slots unless shown otherwise, `--spec 2`, greedy sampling, eight generated tokens, the shipped expert profile, and mmap-backed experts. Because the investigation spans the pre-guard and post-guard revisions, each case records its tested source revision in the JSON.

| Prompt | Layer-major status | Automatic prefill | Layer-major prefill | Automatic / layer-major H2D | Greedy output IDs |
| ---: | --- | ---: | ---: | ---: | --- |
| 4K | Guard fallback | 273.53 tok/s | 272.12 tok/s | 83,264.9 / 83,264.9 MB | Match |
| 8K | Guard fallback | 286.70 tok/s | 317.57 tok/s | 125,804.6 / 125,804.6 MB | Match |
| 16K | Active, two rounds (fresh current-revision retest) | 429.08 tok/s mean | 553.00 tok/s mean | 200,688.6 / 102,274.4 MB | Match in both rounds |
| 32K | Active, two rounds | 544.28 tok/s mean | 625.54 tok/s mean | 382,392.6 / 177,566.7 MB | Match in both rounds |

The 32K mean is based on two interleaved rounds with reversed order in round 2: automatic measured 563.53 and 525.02 tok/s; layer-major measured 622.13 and 628.95 tok/s. The 14.9% prompt-throughput improvement and 53.6% lower reported expert H2D volume apply only to this model, cache size, and machine. Automatic cache sizing did not leave enough scratch VRAM at 32K, so the active comparison fixed both arms at 1,000 slots.

The exact 16,384-token minimum was retested after fixing the off-by-one in the eligibility guard. Both reversed-order rounds entered layer-major and matched all eight generated IDs. Automatic measured 409.51 and 411.00 tok/s; layer-major measured 560.21 and 529.79 tok/s. These two samples document threshold behavior and should not be treated as a general performance estimate.

A fresh two-round retest after rebuilding revision `9b17dc454fd53e4df12259272ab4872df95b69a5` also entered layer-major in both rounds and matched all eight generated token IDs. Automatic measured 395.46 and 462.69 tok/s; layer-major measured 553.62 and 552.37 tok/s. The layer-major arm reported 102,274.4 MB H2D in each round versus 200,688.6 MB for automatic. The machine-readable rows are retained separately under `16384_current_revision_9b17dc45_retest`; this is a second two-round sample, not a replacement for the earlier boundary run.

A separate 8K current-revision check with `--adapt-every 0` did not establish output parity: both arms completed, and the layer-major arm reported the expected `a short prompt` fallback, but the two output sequences differed. Two later automatic-only controls and two later feature-flag fallback controls on the same prompt all produced the same alternate eight-token sequence. Treat the A/B sample as inconclusive; it neither establishes a guard regression nor supports a parity claim. The pair and control summary are retained under `8192_current_revision_fallback_inconclusive`.

A second 16K active-path retest used `docs/DETAILS.md` as a distinct prompt body (SHA-256 `fd904fa30298992cd2c50628310c23d8e48e50a6ff629f3bcb0bcd181d1e14d7`). Both reversed-order rounds matched all eight generated IDs. Automatic measured 384.69 and 438.88 tok/s; layer-major measured 413.90 and 423.66 tok/s. This verifies parity on a second prompt body; it is a small sample and does not establish a general speedup. Rows are under `16384_details_corpus_current_revision_retest`.

Three pre-guard 8K active attempts are also retained in the JSON: cache/target variants each produced a greedy continuation mismatch after the first generated token. The cause is unresolved. These runs are diagnostic evidence, not valid performance comparisons. The current implementation gates prompts below 16,384 tokens to the ordinary path.

An isolated pre-guard diagnostic captured every verify window's FP32 logits while running the ordinary greedy sequence. Both arms chose token `248068` first. At position 8,192, automatic prefill ranked `198` over `271` by only 0.151 logit; layer-major ranked `271` over `198` by 0.961, matching the observed second-token divergence. The final residual hashes already differed at the first verify window (position 8,191), although its argmax remained `248068`. This locates the greedy flip after a prompt-state difference; it does not prove whether the underlying cause is accumulation order, recurrent-state progression, or another numerical effect. The temporary per-window instrumentation is described in the JSON and is not part of the submitted branch.

Prompt token files were generated deterministically by `bench/layer_major_ab.py`; the JSON includes each prompt SHA-256, exact generated IDs, per-run timings, H2D bytes, and sampled peak memory. The OS file cache was not cleared, so these measurements are not cold-cache or physical NVMe-read results. Decode measurements varied, and no decode performance claim is made.

A follow-up one-round check at 16,383 tokens, immediately below the minimum, also reported the explicit short-prompt fallback and exact eight-token parity. Its run-level data is included in `results.json`.

## 500-slot cache limitation

The 16,384-token eligibility threshold does **not** guarantee output parity at smaller expert-cache capacities. Four current-binary checks at 16K with 500 cache slots, using the `docs/DETAILS.md` prompt body and the same exact token IDs, all entered layer-major and returned a different greedy continuation after the shared first token. Automatic began `[248068, 198, ...]`; layer-major began `[248068, 271, ...]`.

| Layer-major setting | Automatic prefill | Layer-major prefill | Automatic / layer-major H2D | Greedy IDs match |
| --- | ---: | ---: | ---: | --- |
| Host residuals, adaptive tiering | 307.30 tok/s | 373.54 tok/s | 543,615.2 / 109,090.9 MB | No |
| VRAM residuals, adaptive tiering | 314.15 tok/s | 388.14 tok/s | 543,615.2 / 109,090.9 MB | No |
| Host residuals, `--adapt-every 0` | 313.00 tok/s | 375.29 tok/s | 543,615.2 / 109,090.9 MB | No |
| Host residuals, 4,096-token super-chunks | 310.53 tok/s | 352.16 tok/s | 543,615.2 / 177,330.9 MB | No |

Each check generated eight tokens. The result persisted across residual storage tier, adaptive-tier freeze, and smaller super-chunks. These timings and H2D counts are diagnostic only and do not constitute successful performance comparisons. The reason for the numerical divergence remains unresolved. Until it is diagnosed and fixed, do not treat 500-slot cache configurations as parity-validated, even when the active path is available. Full compact per-run records are in `results.json` under `low_cache_16k_parity_checks`.

One-round checks at 625 and 750 slots matched automatic and layer-major exactly; both produced `[248068, 271, 248069, 271, 2495, 450, 369, 264]`, consistent with the existing two-round 1,000-slot result. Automatic at 500 slots instead produced `[248068, 198, 760, 1156, 6587, 728, 310, 59987]`. This prompt therefore changes continuation across cache-capacity execution paths. The 625/750 checks are single samples and do not establish a supported minimum; their full rows are in `results.json` under `cache_capacity_controls`.

A forced-continuation diagnostic (`--spec-follow` plus `--window-hashes`, with tier adaptation frozen) sent the automatic 500-slot continuation through both paths. The first verify window at position 16,383 already had different final-residual hashes, although both paths chose token `248068`. At position 16,384, the first row argmax changed from `198` to `271`; the second row argmax remained `198`. All eight final-residual hashes differed. This confirms that the prompt-state difference precedes the observed greedy flip but does not identify which operation causes it. The forced IDs and compact hash files are in `cache500-forced-follow/`; full logs are omitted because they contain the complete tokenized prompt.

An opt-in `STRATA_DUMP_VERIFY_LOGITS` diagnostic captured the first row's raw FP32 logits from each verify window. With the original grouped scatter-add, both paths chose `248068` at position 16,383 and the distributions had KL `1.36e-12`. At position 16,384, automatic favored token `198` over `271` by `0.2896` logit, while layer-major favored `271` over `198` by `0.3419`; the automatic-to-layer-major KL was `0.0495`. A router-order scratch experiment did not change the greedy output and increased this KL to `0.1280`, so accumulation order alone does not explain the observed divergence. That experiment was reverted. The compact top-five and per-row diagnostics are in `results.json` under `cache500_verify_logits_diagnostic`; full logits files remain outside the repository.

A two-round 625-slot retest on the same 16K prompt matched all eight generated IDs in both arms and both rounds, with layer-major active each time. Automatic prefill measured 381.61 and 365.42 tok/s; layer-major measured 379.08 and 392.08 tok/s. H2D volume was 341,247.4 MB for automatic and 77,521.3 MB for layer-major in each run; peak VRAM was 6,358–6,359 MiB and 6,513 MiB respectively. This repeatability sample does not establish 625 slots as a safe minimum: the 500-slot divergence remains unresolved, and there is no evidence between those capacities. It also does not show a throughput gain at 625 slots. The compact records are in `results.json` under `cache625_two_round_validation`.

An `STRATA_PREFILL_MMQ=0` control at 500 slots produced matching IDs, but layer-major explicitly fell back with `the experts are not on MMQ`. It therefore did not exercise the optimized path and is not parity evidence. This confirms the current feature's MMQ dependency; the control summary is retained under `cache500_mmq_disabled_control`.

## 500-slot layer drift and QSA selector diagnostic

A temporary, opt-in diagnostic compared the final prompt row after each complete layer. With the default selector, the layer-0 residual differs by only `9.38e-10` RMS (max `5.96e-8`); by layer 14 the difference is `1.19e-4` RMS. At QSA layer 15, the attention projection difference is `4.13e-3` RMS (max `1.97e-2`), and the hashes of the two selected-cell lists differ (2,051 cells each). The first routed-expert ID ordering difference also appears at layer 15. That route swaps the final two top-10 experts (`209,375` automatic vs `375,209` layer-major); their set is the same. This supports a path where small earlier rounding differences are amplified at QSA selection/attention and then affect later routing. It does not identify the initial layer-0 rounding source. The compact values and hashes are in `results.json` under `cache500_layer_drift_diagnostic`; temporary diagnostic hooks were removed from the source after collection.

As a selector control, setting `STRATA_SELECT_OLD=1` in both arms produced exact eight-token parity in two reversed-order rounds at 500 slots. Automatic measured 267.76/274.12 tok/s and layer-major 360.31/320.28 tok/s; reported H2D was 543,611.2/108,998.5 MB. This does not validate against the default automatic path: the legacy selector changes automatic's continuation too. A test-only arm-specific run with the old selector on layer-major and the default selector on automatic still diverged (`[248068, 198, ...]` vs `[248068, 271, ...]`). Therefore the selector control is diagnostic, not a fix or a performance comparison. Full run records are in the untracked local harness output directories `cache500-old-qsa-selector-two-round/` and `cache500-lm-only-old-qsa-selector/`.


A final schedule control at 500 slots set --layer-major-tokens 1280, so each layer-major super-chunk contained only one 1,280-token prompt chunk. The optimized path remained active but diverged on generated token 2: automatic [248068, 198], layer-major [248068, 271]. This rules out combining multiple prompt chunks inside one super-chunk as the sole explanation for the low-cache parity failure. The run generated two tokens, so it is a diagnostic only. Run metadata is in results.json under cache500_one_chunk_superchunk_control; raw files are in the untracked local cache500-one-chunk-superchunks/ directory.


## Low-cache fallback guard

The 16K/500-slot mismatch now falls back before entering layer-major when the allocated expert cache has fewer than 822 slots. The CLI setting `--expert-cache 500` produced 656 allocated slots (506 lent to the prompt); two reversed-order runs used the fallback and matched automatic for all eight generated tokens. The lowest active configuration with repeated parity evidence used `--expert-cache 625`, which allocated 822 slots, and matched the same prompt in two rounds. This is a conservative guard based on the available measurements, not a general parity guarantee at 822 slots or above. Run-level evidence is under `cache500_cache_floor_fallback_validation`; the raw local logs are in `cache500-cache-floor-fallback-822/`.


A test-only MMQ control limited layer-major groups to one expert while bypassing the cache-floor guard for diagnosis. At 500 requested slots, the active path still diverged on token 2 (`[248068, 198]` automatic vs `[248068, 271]` layer-major). MMQ group count rose from 15,229 to 238,842, while reported layer-major H2D stayed near 415,295 MB. This rules out combining multiple experts in a single MMQ group as the sole cause. The run generated two tokens and is not a performance comparison. The temporary override was removed and the committed source rebuilt; details are under `cache500_single_expert_group_diagnostic`, with raw local logs in `cache500-single-expert-groups/`.


A temporary stage dump localizes the first measured 16K/500-slot divergence to layer 0's FFN half: the final prompt row is bitwise identical after attention, then differs by max `5.96e-8` (RMS `9.38e-10`) after FFN/expert processing. The difference therefore precedes QSA, which later amplifies it. With `STRATA_GR_UNFUSED=1` in both arms, that FFN residual drift shrank but remained (max `2.24e-8`); both arms then chose token 271 because automatic itself changed from its default token 198. Applying unfused mode only to layer-major still yielded 271 and did not match default automatic. This path change is not a fix. The stage-dump code was removed and the committed source rebuilt. Compact measurements are under `cache500_layer0_stage_diagnostic`; raw local records are in `cache500-layer-stage-dump/` and `cache500-layer-stage-unfused/`.


A second FFN-boundary capture confirms the last prompt row's layer-0 router IDs and weights match bitwise, as does the shared-expert output. The combined MoE output differs slightly (max `2.38e-7`, RMS `6.39e-9` across 2,560 values). Together with the equal post-attention residual, this narrows the first drift to routed expert product values or their accumulation. A single-expert-per-group experiment still diverged, and the router-order accumulation experiment did not restore parity; the exact source remains unresolved. Temporary instrumentation and the diagnostic cache-floor bypass were removed, and the committed source was rebuilt. See `cache500_ffn_boundary_diagnostic`; raw vectors are retained only in the local `cache500-layer-ffn-diag/` run directory.


A targeted last-row capture confirms the exact cause of the first low-cache drift. At layer 0, automatic and layer-major have identical routing IDs and weights, identical shared-expert output and gate, and bitwise-identical output vectors for all ten selected experts. Their combined MoE vectors differ only by FP32 rounding (max `2.38e-7`, RMS `6.39e-9`). Automatic accumulates ten weighted FMA terms in router order from zero and adds the gated shared output afterward. Layer-major sums per-expert group rows and adds those sums in expert/group order to an accumulator already initialized with the shared output. The output difference is therefore reduction order/placement, not different routing or expert math; later QSA can amplify it into a greedy token flip. Details are under `cache500_fp32_reduction_order_diagnostic`; the raw small vector dumps remain local in `cache500-layer-ffn-diag/`, `cache500-per-expert-rows/`, and `cache500-gate-rows/`. Diagnostic hooks and the cache-floor bypass were removed and the committed source rebuilt.


The committed 822-slot cache floor was checked on the current binary: `--expert-cache 625` allocated exactly 822 slots, the layer-major path remained active, and it matched automatic for all eight generated IDs on the 16K `docs/DETAILS.md` prompt. This is one boundary sample and does not broaden the parity guarantee. The layer-major arm measured 337.47 tok/s vs 360.44 automatic and reported 272,506.3 MB vs 341,247.4 MB H2D; this sample is not a performance claim. Run details are under `cache625_current_guard_boundary_validation`; raw logs are local in `cache625-cache-floor-boundary/`.


A temporary direct-FMA scatter control carried each token accumulator across group launches, removing the separate per-group sum rounding. It still diverged on token 2 (`[248068, 198]` automatic vs `[248068, 271]` layer-major), because contributions continue to arrive in expert/group order instead of each token's router order. The extra scratch-free reducer was reverted; it is not a fix. Run metadata is under `cache500_direct_fma_accumulator_control`; raw logs are local in `cache500-singlepass-fma/`.


A two-round retest on the committed cache-floor build used `--expert-cache 625` (822 allocated slots, 679 lent to the prompt). Layer-major remained active in both reversed-order rounds and matched all eight generated IDs. Automatic measured 372.88/381.88 tok/s; layer-major measured 375.82/376.30 tok/s (means 377.38 vs 376.06), so no throughput gain is claimed. Reported expert H2D was 341,247.4 MB automatic vs 77,521.3 MB layer-major per run; peak VRAM was 6,380–6,393 MiB automatic and 6,548–6,552 MiB layer-major. This is a repeatability sample for one prompt and cache configuration, not a general parity guarantee. Structured rows are under `cache625_current_guard_two_round_validation`; raw logs remain local in `cache625-current-two-rounds/`.
